# Target: Crossbar.io, single node

One [Crossbar.io](https://crossbar.io) router, three realms, and nine [AutobahnPython](https://github.com/crossbario/autobahn-python) clients running a seeded workload. The router configuration and the client code are published here in full. Only the keys stay out of the repository.

## The system under test

Everything in the path of a WAMP call is part of the target: the protocol stack, the interpreter, the TLS library and the event loop. Each of them affects behaviour and performance, and each can carry a bug or an exploit.

| layer | router | clients |
|---|---|---|
| machine | one KVM/QEMU virtual machine, Debian 13 | one KVM/QEMU virtual machine per client (nine), Debian 13 |
| host | Debian 12 | the same host |
| network | TCP between the virtual machines | |
| interpreter | CPython 3.14 | CPython 3.14 |
| software | Crossbar.io on Twisted, epoll reactor (`CROSSBAR_REACTOR=epoll`) | AutobahnPython on asyncio, `_UnixSelectorEventLoop` with `EpollSelector` |
| TLS | pyOpenSSL over `cryptography`, which bundles **its own OpenSSL** | the CPython `ssl` module, with **the OpenSSL CPython was built with** |
| WAMP transport | WebSocket over TLS, no WebSocket extensions (no compression); RawSocket over TLS is also offered | WebSocket over TLS |
| serializer | CBOR | CBOR |
| authentication | anonymous (`public`), WAMP-Cryptosign (`application1`, `application2`) | the same |

**The two ends of a connection run different TLS stacks.** The router's TLS goes through the OpenSSL that `cryptography` bundles; the clients' TLS goes through the OpenSSL CPython was built with. Their versions differ.

**Every run records what it actually ran on.**
- Each client writes a `start` record into its log, holding the interpreter, the OpenSSL version, the library versions and the event loop.
- Each `join` record holds the WebSocket extensions actually negotiated on the live connection; there must be none.
- The smoke test prints the router's stack next to the clients' stack.

The smoke test on 2026-11-13 measured:

| | router | clients |
|---|---|---|
| interpreter | CPython 3.14.7 | CPython 3.14.7 |
| TLS | OpenSSL 4.0.3 (`cryptography` 50.0.2, pyOpenSSL 26.4.0) | OpenSSL 3.5.8 |
| WAMP | Crossbar.io 26.11.1.dev2, AutobahnPython 26.11.1, Twisted 26.10.0 | AutobahnPython 26.11.1, txaio 26.6.1 |
| CBOR, Cryptosign | cbor2 6.2.1, PyNaCl 1.6.2 | cbor2 6.2.1, PyNaCl 1.6.2 |

This measurement comes from the test machine. The deployed virtual machines record their own values, and a match result carries them.

The smoke test's call latencies show that the target works. They are not a benchmark: measuring robust round-trip times, such as a p99, is a separate task, and so are faster variants of the target (for example PyPy).

## The router

[`.crossbar/config.json`](.crossbar/config.json) defines one listening transport of type `universal`, on port 8080 over TLS. On every connection the router tells three protocols apart:

- **WAMP over WebSocket**, at path `/ws`;
- **WAMP over RawSocket**, on the same port;
- **HTTPS**: the static files in [`web/`](web/), the web share.

WAMP uses the CBOR serializer. There are three realms with three clients each:

| realm | authentication | role | clients |
|---|---|---|---|
| `public` | anonymous | `guest` | `client01`, `client02`, `client03` |
| `application1` | WAMP-Cryptosign | `device` | `client04`, `client05`, `client06` |
| `application2` | WAMP-Cryptosign | `device` | `client07`, `client08`, `client09` |

Each role may call, register, publish and subscribe under the URI prefix `gladiators.`, and nowhere else. Caller and publisher disclosure is on, so a callee sees the caller's authid as the router reports it.

### Keys

There is no key material in this repository.

- **The TLS key and certificate** (`.crossbar/server.key`, `.crossbar/server.crt`) are generated by each deployment. For a local run, make a self-signed pair for `localhost`:

  ```console
  openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes -keyout .crossbar/server.key -out .crossbar/server.crt -days 30 -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost"
  ```

- **The Cryptosign principals** `client04` to `client09` start with empty `authorized_keys`. Each client generates its own key on its first start, and a deployment adds that client's public key to its principal in `config.json`, in both transports. A public key is not key material: the private key never leaves its client. While a principal's list is empty, the router refuses it.

## The client

Each client runs [`client/workload.py`](client/workload.py). It needs AutobahnPython with asyncio, CBOR and Cryptosign support. [`client/pyproject.toml`](client/pyproject.toml) declares that, with AutobahnPython pinned to the exact release the clients run, and [`client/uv.lock`](client/uv.lock) holds the exact set of packages, with their hashes. Every client runs that set, however much later it is installed. From the repository root:

```console
uv sync --frozen --project targets/crossbar/single-node/client
```

makes the venv `targets/crossbar/single-node/client/.venv` from the lock; `--frozen` installs the lock as committed and fails if it no longer matches `pyproject.toml`. A change of the dependencies is a change of `pyproject.toml` followed by `uv lock` in `client/`, committed together; `just check` refuses a lock that is out of date.

A client:

1. joins its realm, anonymously or with its Cryptosign key, and tries again forever if the connection drops or the join is refused (see "Retrying" below);
2. registers `gladiators.<name>.echo`, which returns `{payload, callee, caller_seen}`;
3. subscribes to every topic under `gladiators.` (a prefix subscription), so every event of its realm's namespace reaches its log (competitions#24);
4. waits until the `echo` of every peer answers (see "Start-up" below);
5. in a loop driven by `--seed`, calls a random peer's `echo` with a payload of 16 to 1024 bytes (`--rate` calls per second on average), and publishes a tick carrying its realm, its name, a sequence number and the digest of a flag on about every second iteration, with `exclude_me=False`, so it receives its own ticks too (see "Flags" below);
6. checks every answer:
   - the payload comes back unchanged;
   - the answer comes from the peer it called;
   - the router reported the caller's own authid to the callee;
   - every event it receives is a tick on `gladiators.tick`, of the expected shape, from its own realm;
   - a tick that names this client as its publisher carries a digest this client published, and comes back once.

With `--duration` the client stops in two phases: it stops calling, waits for its call in flight, keeps answering `echo` for `--stop-grace` seconds (default 5) while its peers finish, and only then leaves.

Every event becomes one JSON line in `--log`: connect, join, refused join, peer ready, waiting for peers, workload start, call, publish, received event, leave, disconnect, and a final summary. A record carries a timestamp, the operation, the peer, the latency in ms, `ok` or the error, and a `violation` field whenever a check fails. Call latency (for example the p99) and the error rate come straight out of these logs.

**Writing the log does not hold up the client** (competitions#19). A record's timestamp is taken when the event happens; a thread of its own then writes the records in order to a file opened with `O_DSYNC`, so each write is durable when it returns. Before, the client wrote and fsync'd every line on its event loop. With the log on NFS, every record then waited for a round trip to the server, and every 194-byte record re-sent its 4 KiB page: 51 MiB/h of NFS traffic per client, for 4 MB/h of log. A crash loses the records still queued, normally the one in flight. The `summary` record's `log_backlog_max` says the deepest the queue got. A log that cannot be written ends the client with exit code 3.

### Flags

**Every tick has a flag** (competitions#21), and **carries only the flag's digest** (competitions#24): the payload is `{realm, name, seq, digest}`, where `digest` is the SHA-256 of the flag's UTF-8 bytes, as 64 hex characters. The flag is autobahn's token, `generate_token(7, 4)`, fresh for every tick: 7 groups of 4 characters such as `K7AT-TMJS-WT47-SEER-3ELJ-UUYM-WRXF`. The alphabet is autobahn's `DEFAULT_TOKEN_CHARS`, 27 characters without look-alikes (no 0/O, 1/I, 2/Z, 8/B), so 28 characters carry 133 bits, and a flag can be read and copied by hand. The characters come from the operating system's generator (`random.SystemRandom`), never from the generator `--seed` drives, which repeats from its seed. `seq` counts the client's ticks from 1 and restarts with the process, so the flag, not `seq`, identifies a tick.

**The publisher records each flag, and nobody else does.** The `publish` record holds the tick's `seq` and `flag`, also when the publish failed, since a failed publish may still have reached subscribers. No event carries a flag: subscribers, the router and anyone else who sees a tick see only the digest. So a flag found in the logs is always in its publisher's record, which says which client published it, on which realm, and when.

**Every received event is recorded** with its topic, the publisher, realm, `seq` and digest it states, and `publisher_seen`, the publisher's authid as the router disclosed it. A received field longer than 80 characters is recorded as its type and length only.

**What a digest and a flag show.** `application1` and `application2` admit only their Cryptosign principals.
- A **digest** of an app-realm tick, held by anyone who is not a member of that realm, shows that an event of the realm reached them. A digest of `public` shows nothing of the kind, since anyone may subscribe there: it is a control.
- A **flag** never travels in an event, so a flag held by anyone but its publisher shows that the publisher's log, share or process was read: beyond WAMP.
- An **event on an app realm that no member published** shows that someone got an event delivered there: the other direction.

**The referee checks presented digests and flags** with [`referee/verify_flags.py`](referee/verify_flags.py) (competitions#22, #24), standard library only:

```console
python3 -I referee/verify_flags.py --logs <dir> --claims <file> --start <iso> --end <iso>
```

- `--logs` is searched for `*.jsonl`, also in subdirectories.
- A claim line is a digest or a flag, optionally followed by the UTC time the player says it obtained it. Case does not matter.
- `--start` and `--end` are the match window.

For each claim it prints one line:
- `counts`: a digest of a flag published on `application1` or `application2` within the window. The line names the client, the realm, `seq` and the publish time.
- `control`: a digest of a flag published on `public` within the window.
- `obtained`: a flag itself, published within the window, on any realm. Flags are totalled apart from digests.
- `invalid`, with the reason: neither a digest nor a flag, in no publish record, published outside the window, claimed before it was published, presented twice, or in more than one publish record.

At the end come the totals, for digests and for flags. The verdict is the referee's, not the tool's. `--self-test` runs its checks.

**The referee traces every received event** with [`referee/verify_events.py`](referee/verify_events.py) (competitions#24), standard library only:

```console
python3 -I referee/verify_events.py --logs <dir> --start <iso> --end <iso>
```

For every event recorded by a client of `application1` or `application2` within the window:
- `matched`: the digest is in exactly one publish record, which states the same publisher, realm and `seq`, was published on the subscriber's realm, and this subscriber has not recorded the digest before.
- `injected`, with the reason: another topic than `gladiators.tick`, no digest, a digest in no publish record, a publish record that states otherwise, one of another realm, or a second copy at the same subscriber.

It prints one line per injected event and, per realm and subscriber, the number matched, the number injected, and the number whose `publisher_seen` differs from the publisher the event states.

**After `leave`, a client issues no call and no publish until its next `join`.** A `call` or `publish` record with `ok: false` is therefore always a request that was sent: a call in flight when the session ends (for example `wamp.close.transport_lost` when the router stops) fails and keeps its record, once. Nothing is sent on a session the client already knows is gone (competitions#15).

Prove that every check fires on its own case:

```console
python client/workload.py --self-test
```

Create a client key (mode 0600) and print its public key:

```console
python client/workload.py --generate-key client04.key
```

Run a client:

```console
python client/workload.py --name client04 --realm application1 --key client04.key --peers client05,client06 --url wss://localhost:8080/ws --trust .crossbar/server.crt --seed 1 --log client04.jsonl
```

Use `--url rss://localhost:8080` for RawSocket. Without `--key` the client authenticates anonymously, which only the realm `public` admits.

### Start-up: no client depends on another starting first

Every client is callee and subscriber (it registers its `echo` and subscribes to the tick right after joining) as well as caller and publisher. Before its workload makes the first call, it waits until the `echo` of every peer answers. This barrier has **no deadline** by default: a deployment may start its clients minutes apart, for example one machine at a time, and a call to a peer that has not started yet would fail for a reason that has nothing to do with the router. A peer that never comes is visible: every 30 seconds the client logs a `peer_wait` record naming the peers still missing. `--peer-wait N` gives up after N seconds instead, logs `peer_ready` with `ok: false` for each missing peer, and starts anyway; the smoke test uses 60, so a client that never starts fails it instead of hanging it.

When its barrier is passed, a client logs `workload_start`. **A match's measurement window starts at the latest `workload_start` across all clients**: records before it belong to the start-up, not to the match.

### Retrying: a refused join backs off

A client never gives up, but it retries two kinds of failure at two different paces:

- **A transport failure** (the router is not up yet, the connection is refused, a TLS error): it retries within 5 seconds at most. This is what lets clients and router start in any order.
- **A refused join** (for example `wamp.error.not_authorized`, a key the router does not know yet): it retries after 5 seconds, doubling with each refusal in a row (5, 10, 20, ..., capped at `--refused-max-delay`, default 300). A refusal does not go away by itself: until the router is given the client's key, retrying fast only costs the router a TLS handshake and an authentication each time, and an expected refusal looks like an unknown key trying its luck. Each `refused` record carries `attempt` (refusals in a row) and `next_s`, the delay before the next attempt. That is an upper bound: autobahn's retry jitter (10 %) can make the actual delay a little shorter, which keeps clients refused together from retrying in step.

A successful join resets both. Once the router knows the key, the client joins within `--refused-max-delay` seconds; restarting the client joins at once.

## Smoke test

[`smoke.sh`](smoke.sh) runs the whole target on one machine:

1. it copies the node directory to a temporary directory;
2. it generates a throwaway TLS pair and throwaway client keys there;
3. it starts the router on the epoll reactor and the nine clients for `DURATION` seconds (default 120), and prints the stack of both ends;
4. it requires every client log to show calls and ticks from its own realm, with no errors, exactly the violations the injected events of step 6 must cause, and every WebSocket connection to have no extensions negotiated;
5. it requires the router to refuse an unknown Cryptosign key (`wamp.error.not_authorized`) and an anonymous client in `application1` (`wamp.error.no_such_role`), and each of those two clients to back off after every refusal;
6. [`smoke_inject.py`](smoke_inject.py) joins `application1` as a second session of `client04` and publishes three events no member published as such: a second copy of another member's tick, a tick that names `client05` with a digest nobody published, and an event on `gladiators.smoke.unexpected`. Each member must record the off-topic event as a violation; `client05` must reject the tick forged as it, and the publisher of the copied tick the copy;
7. it requires every `publish` record to hold a `seq` (1, 2, 3, ...) and a flag of 7 groups of 4 token characters, no flag twice across the nine logs, no flag in any other record, and every received tick to carry the digest of a published flag (but the forged one); and the verifier's copy of the token alphabet to be autobahn's;
8. it gives `verify_flags.py` five claims: the digest of a flag of each app realm and of `public`, a flag of `application2` itself, and a value of the flag's form outside its alphabet. It requires `counts`, `counts`, `control`, `obtained` and `invalid`;
9. it runs `verify_events.py`, and requires exactly three injected events at each member of `application1`, none on `application2`, and matched events at every member.

From the repository root:

```console
just smoke ~/work/autobahn-crossbar/crossbar/.venvs/cpy314/bin/crossbar 18080
```

The first argument is the `crossbar` executable (default: `crossbar` on the `PATH`), the second the port (default 8080). The recipe makes the client's venv from its lock (`uv sync --frozen`, as in "The client" above) and runs the test with it, so the client under test is always the locked one.

`smoke.sh` itself takes them from the environment: `PYTHON` (the python of the client's venv), `CROSSBAR` and `PORT`; the defaults are `python3`, `crossbar` and 8080. It checks the first two before it starts, and stops with a message naming the variable. When the port is already taken, it refuses to start and names the port. To keep it off the host's network, run it in its own network namespace:

```console
unshare -rn --pid --fork --mount-proc just smoke
```
